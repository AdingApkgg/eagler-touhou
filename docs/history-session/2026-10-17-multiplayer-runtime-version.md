# 联机程序版本一致性

普通已安装游戏保留离线优先。已安装 MP 的房间预缓存曾丢弃
`checkForUpdate` 句柄，短暂“检测游戏”启动也跳过后台更新，导致这两个入口
不能保证更新 MP 程序。正式开局虽有 ACK 后检查，但仍可能先打开不同旧版本。

现在房间准备、每次准备按钮和检测游戏先完成当前 MP 程序的清单与完整性检查，
失败不回退旧版本。没有 App Shell worker 时仍使用统一程序缓存或经过验证的 HTTP。
普通与 MP 通过各自 Manifest group 区分，互不代替。

准备消息携带 `runtimeGeneration`，Relay 对版本化房间检查所有已准备玩家一致，
将版本固定到本局，并在信令与游戏连接上核对。未知版本旧客户端不能混入新客户端
的开局。新前端遇到不支持版本校验的旧 Relay 会阻止准备。全旧协议/开发房间
仍保留兼容行为，不能将该兼容行为描述为已验证程序一致性。

实际房间配置在 native ready 后才生成，因此程序约束提前进入初始 Runtime 计划。
准备后又发版时，启动检查拒绝清单与本局约定不符，需重新进入房间并准备。
运行中不替换程序。MP 本地录像和文件访问仍可离线。

改动仅涉及共享 Launcher/Relay，没有修改或重建各作品 SP/MP 原生分支。
上线需要前端和 Relay 同时更新。当前未部署。

验证：类型检查、Launcher 构建、程序选择测试、实际本地 Relay 双端连接、
准备服务的针对性用例，以及 Chromium/Firefox/WebKit 的实际 Service Worker
与 CacheStorage 场景。浏览器使用合成 HTML/JS/WASM；不代表原生对局或实体设备验收。
房间服务回归 44 项、准备/Runtime 服务回归 68 项通过。后者的筛选意外包含了
两条旁观服务所有者单测，均通过；没有重跑旁观浏览器或原生对局验收。
WebKit 使用独立探针确认的断网模拟兼容路径。
